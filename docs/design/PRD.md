## 背景：AI 时代开发者信息入口的范式转移

### 开发者了解社区项目的入口正在重构

过去十年，开发者了解一个开源社区项目的路径是稳定且可预测的：

```
搜索引擎 → 项目官网 / GitHub 仓库 → 阅读文档、教程、博客 → 形成认知
```

社区运营团队通过 SEO 优化确保官网在搜索结果中排名靠前，开发者"先搜索、再点击、再阅读"的行为模式让官网始终是信息的**第一触点**。在这个模式下，SEO 即可见性——排名越高，触达越多。

从 2023 年起，这一路径正在被快速重构。开发者越来越习惯直接向 ChatGPT、DeepSeek、Gemini 等生成式 AI 平台提问，由 AI 综合多个信息源后直接给出答案。新的路径变为：

```
AI 问答平台 → 直接获得合成答案 → 认知形成（可能从未访问官网）
```

关键变化在于：**开发者获取信息的"第一触点"不再是官网，而是 AI 生成的回答本身**。AI 是否引用了官方文档作为回答来源，决定了社区内容能否在这一新路径中被开发者"看到"。如果 AI 未引用官方内容，开发者的认知将完全基于第三方信息——可能是过时的、不准确的、甚至是竞品的内容。

这意味着社区在 AI 时代面临一个全新问题：**不是"搜索结果中排第几"，而是"AI 回答中是否被引用"**。

### GEO：生成式搜索时代的可见性优化

SEO（Search Engine Optimization）解决的是传统搜索引擎中的**排名可见性**问题——让官网出现在搜索结果的前几页。其核心假设是：开发者会点击搜索结果、访问官网、自行阅读。

GEO（Generative Engine Optimization）解决的是生成式 AI 搜索中的**引用可见性**问题——让 AI 平台在回答中引用官方内容作为来源。其核心假设是：开发者不再主动点击链接，而是直接信任 AI 给出的答案。

两者的本质区别：

| 维度 | SEO | GEO |
|------|-----|-----|
| 目标 | 搜索结果排名靠前 | AI 回答中引用官方来源 |
| 评估方式 | 关键词排名、流量统计 | AI 平台引用率、引用准确性 |
| 优化对象 | 页面标题、Meta 标签、外链 | 内容结构化程度、权威信号、可引用性 |
| 用户行为 | 搜索→点击→阅读 | 提问→获得答案→（可能不访问官网） |


GEO 不是 SEO 的替代，而是 SEO 在生成式搜索时代的必要延伸。社区运营需要在传统 SEO 之外，系统性评估和优化官方内容在各 AI 平台中的引用表现——这正是本系统要解决的问题。

## 一、问题陈述

### 问题现状

开源社区运营团队在 AI 搜索时代面临一个新的可见性盲区：

1. **无感知** — 社区无法系统性地知道用户向 ChatGPT、DeepSeek 等 AI 平台提问时，AI 是否引用了官方文档作为回答来源
2. **无方向** — 即便感知到 AI 引用率低，也缺乏系统性的优化路径，不知道应该先改哪个页面、怎么改
3. **无闭环** — 内容优化工作无法量化效果，无法判断某次改动之后 AI 引用率是否提升
4. **无自动化** — 目前只能靠运营人员手动向 AI 平台提问抽查，费时且覆盖面极低

### 当前工作流程（现状）

```
运营人员手动向 AI 平台提问 → 人工判断回答是否引用了官方内容
→ 缺乏优化建议 → 内容团队凭经验改文档 → 无法评估效果
```

这一过程高度依赖个人经验，且覆盖面极为有限（通常只能抽查几个问题），无法形成系统性认知。

### 影响分析

**对运营团队的影响：**
- 不知道官方内容在 AI 平台中的实际表现，无法向管理层汇报 GEO 覆盖率
- 内容优化工作缺乏优先级依据，投入产出不透明
- 与竞品社区相比，GEO 能力差距无法量化

**对用户的影响：**
- 用户通过 AI 平台提问时，可能获取到过时的第三方信息而非官方答案
- 社区官网产出的优质内容无法触达通过 AI 搜索的用户群体

### 为什么现在解决

- AI 搜索平台（ChatGPT、DeepSeek、Gemini 等）用户规模快速增长，正在取代传统搜索引擎成为开发者的第一信息入口
- 竞品社区已开始在 GEO 方向布局，不行动即意味着持续落后
- 现有 Claude Code Skill 机制可以以极低成本构建自动化评估流水线，技术可行性已验证

## 二、目标与目的

### 业务目标

1. **建立基线** — 为目标社区建立 GEO 引用率基线，量化"官方内容在各 AI 平台中的覆盖率"
2. **驱动改进** — 将评分结果转化为可执行的 Issue，推动内容团队持续优化
3. **持续监测** — 定期（建议每周）自动重新评估，追踪引用率随时间的变化趋势

### 用户目标

1. **可见性** — 运营团队能随时查看各问题在各 AI 平台的引用情况报告
2. **可操作性** — 每个低引用率问题都有对应的 GEO 改进建议，标注优先级
3. **低门槛触发** — 无需了解 AI 技术细节，一行指令即可触发完整评估流程

### 非目标（明确不做）

- 不评估 AI 回答的语义质量（仅判断是否引用官方 URL）
- 不自动修改官网内容（系统只输出建议，执行靠人工）
- 不提供 Web 可视化界面（Claude Code 对话驱动，Phase 3 再考虑）
- 不做实时监控（批量周期评估场景）

## 三、用户画像

### 主要用户：社区运营者

**特征：**
- 负责开源社区的内容建设、SEO/GEO 优化工作
- 定期向管理者汇报社区曝光质量
- 熟悉 CLI 操作和 Git，无需了解 AI 技术原理

**需求：**
- 了解官方内容在各 AI 平台中的引用覆盖率
- 获得优先级明确、可直接交给内容团队执行的改进建议
- 追踪历次优化的改善效果

**痛点：**
- 人工抽查耗时且覆盖面不足，无法形成系统性评估
- 缺乏从"评分结果"到"具体优化行动"的转化路径

**典型场景：** "每周一上午，系统自动运行完整评估，我直接查看 assessment-report.md 了解本周各问题的 AI 引用情况，重点关注新出现的 P0 问题，推动内容团队认领对应的 GitHub Issue。"

---

### 次要用户：内容贡献者

**特征：**
- 根据 Issue 分配执行具体内容优化任务的技术写作者或开发者
- 不操作本系统，但是系统输出（Issue 内容）的直接消费者

**需求：**
- 清楚理解 Issue 背后的问题现象和根因分析
- 知道具体需要改什么（action items）
- 能验证修改效果（下次复检结果追加到 Issue 评论中）

**典型场景：** 收到 Issue 指派后，修改官方文档内容并提交 PR；PR 合并后系统自动触发新一轮 GEO 检测，将最新引用率评分追加到对应 Issue 评论中，验证内容改进是否带来了引用率提升。

## 四、需求概述

系统由 6 个核心功能模块组成，通过 `AGENT.md` 编排为一条自动化流水线。

### Epic 1：问题集生成（get-question）

**用户故事：**
```
作为社区运营者，
希望系统能从论坛、Issue、邮件列表、官网搜索热词等真实用户行为数据中
自动提取并整理出代表性的搜索问题集，
以便用于后续的 AI 平台采样和评估。
```

**验收标准:**
- [x] 支持从论坛热帖、仓库 Issue、邮件列表、官网搜索热词 4 条路径获取问题，任意单条路径失败不中断其余路径，失败路径在 stderr 输出 WARNING
- [x] 支持手动补充问题，手动补充的问题与自动生成的问题使用相同的字段结构和 `id` 编号规则
- [x] 语义相似的问题被自动去重，新问题仅追加到问题集末尾，不修改已有条目的 `id`、`official_urls` 和 `note` 字段
- [x] 每个问题的 `doc_form` 字段自动推断为 T / H / R / E / F 之一，不允许为空
- [x] 输出的 `questions.json` 和 `questions.md` 格式符合系统数据模型规范，`questions.md` 中序号与对应问题的 `id` 后缀全局一致

**优先级：** P0

---

### Epic 2：官方 URL 预填充（prefill-urls）

**用户故事：**
```
作为社区运营者，
希望在 AI 平台采样之前，系统能自动为问题集中每个问题
发现并验证对应的官方文档 URL，
以便确保评分阶段有准确的参照基准，减少人工标注负担。
```

三层审计逻辑：(1) 官方内容是否存在；(2) URL 路径是否与 `doc_form` 匹配（如教程型问题对应 `/tutorial/` 路径）；(3) HTTP HEAD 验证 URL 可达性。已标注的 `official_urls` 不会被覆盖，仅补填空白条目。结果写回 `questions.json`，标注置信度供人工 review。

**验收标准:**
- [x] 三层审计（内容存在性 → doc_form 路径匹配 → HTTP 可达性）全部执行，任意层审计失败的 URL 不写入 `official_urls`
- [x] 已有 `official_urls` 的问题不被覆盖，仅补填 `official_urls` 为空的条目，不修改其他字段
- [x] 每条候选 URL 经 HTTP HEAD 请求验证可达性（2xx/3xx 视为可达），不可达 URL 在 stderr 输出 WARNING 并跳过
- [x] 每条补填结果附带置信度分数（0–1），置信度低于阈值的条目在 Markdown 输出中标注 `[需人工核查]`
- [x] 更新后的 `questions.json` 只修改目标字段，不影响 `id`、`question`、`note` 等字段内容

**优先级：** P0

---

### Epic 3：AI 平台采样（platform-chat）

**用户故事：**
```
作为系统，
希望能向 ChatGPT、DeepSeek、豆包、Qwen、Gemini、Kimi 等主流 AI 平台
批量发送问题并收集回答，
以便获取各平台对官方内容的引用情况。
```

自动检测 `.env` 中有效的 API Key，仅对有 Key 的平台发起请求；单平台失败不中断整体采样；支持 `append` 模式追加补充采样。当前支持 6 个平台：ChatGPT、DeepSeek、豆包、Qwen、Gemini、Kimi。

**验收标准:**
- [x] 系统启动时自动检测 `.env` 中各平台 API Key 的有效性，未配置 Key 的平台跳过且不报错，stderr 输出已启用平台列表
- [x] 单平台请求失败（超时、限流、认证失败等）时，该平台标记为失败并跳过，其余平台继续采样，整体流程不中断
- [x] `append` 模式下，已有采样结果的问题仅追加新平台数据，不覆盖或修改已有平台的回答
- [x] 输出 `responses.json`，包含每个问题在每个可用平台的回答文本和提取的引用链接列表，格式符合 scoring-engine 输入规范
- [x] 运行结束后在 stderr 输出采样摘要，包含成功/失败/跳过的平台数和问题覆盖数量

**优先级：** P0

---

### Epic 4：评分与诊断（scoring-engine）

**用户故事：**
```
作为系统，
希望能将 AI 平台回答中的引用链接与官方 URL 进行匹配，
计算每个问题的引用率并结合内容形态给出针对性改进建议，
以便量化社区内容在各 AI 平台的覆盖情况。
```

**验收标准:**
- [x] 每个问题的评分状态为 `satisfied`、`not_cited`、`no_official_content` 三者之一，无遗漏，无其他值
- [x] 评分逻辑仅基于 URL 字符串匹配，不调用 LLM，相同输入在任意环境下产生相同评分结果（可重现）
- [x] 评分依据 `≥75% 平台引用` 作为 `satisfied` 门槛；低于门槛时状态为 `not_cited`；`official_urls` 为空时状态为 `no_official_content`
- [x] 每个 `not_cited` 或 `no_official_content` 问题根据其 `doc_form` 字段选择对应诊断路径，并从 GEO 建议目录中匹配至少 1 条适用建议
- [x] 输出 `scoring-results.json`，包含每个问题的评分状态、各平台引用明细、诊断结论和改进建议列表，格式符合 issue-creator 输入规范

**优先级：** P0

---

### Epic 5：Issue 创建与追踪（issue-creator）

**用户故事：**
```
作为社区运营者，
希望系统能将低引用率的问题自动整理为 GitHub / GitCode Issue，
每个问题对应一个 Issue 并在每次复检后追加最新评分变化，
以便内容团队统一管理和认领优化任务。
```

**验收标准:**
- [x] 每个 `question_id` 最多对应一个 Issue，重复运行时已有 Issue 不被重新创建，`issue-map.json` 记录映射关系并跨运行持久化
- [x] 新建 Issue 标题严格符合格式 `【GEO】[{id}][{doc_form_label}·{status_label}] {question}`，标签包含 `doc_form` 对应分类
- [x] 已有 Issue 的问题在复检后追加评论，评论包含最新 `citation_rate`、评分状态及与上次评估的对比
- [x] 当问题评分状态变为 `satisfied` 时，在追加的评论中明确建议关闭该 Issue
- [x] 同时支持 GitHub 和 GitCode 两个平台，通过 `.env` 中的仓库 URL 自动识别目标平台；`dry_run=true` 时只打印操作计划，不实际创建或更新 Issue

**优先级：** P0

---

### Epic 6：评估报告（assessment-report）

**用户故事：**
```
作为社区运营者，
希望每次评估结束后能获得一份包含全量问题覆盖情况的报告，
清晰展示各平台引用状态和与上次评估的趋势对比，
以便向管理层汇报 GEO 改进进展。
```

**验收标准:**
- [x] 同时生成 `scoring-report.json` 和 `scoring-report.md` 两种格式，Markdown 报告在标准 Markdown 渲染器中可正常阅读
- [x] 报告按 `satisfied` / `not_cited` / `no_official_content` 三类分组展示所有问题，每类分组显示问题数量汇总
- [x] 每个问题条目展示各平台引用指示符（✅ 已引用 / ❌ 未引用 / — 未采样）、综合引用率，以及关联 Issue 的链接（若存在）
- [x] 报告包含与上次评估的趋势对比，标注引用率变化幅度（↑/↓/—），并汇总新增改善和新增退化的问题数量
- [x] 报告生成过程无需人工干预，可作为评估流水线最后一步自动执行；在无历史评估数据时，趋势列显示"首次评估"而非报错

**优先级：** P0

## 五、成功指标

### 核心指标（North Star）

**指标：** 社区内容 GEO 覆盖率
**定义：** `satisfied` 状态问题数 / 总问题数 × 100%
**当前基线：** MindSpore 首次评估结果待测；openEuler 首次评估：0%（50 题全部 `not_cited`）
**目标：** 6 个月内将 P0 问题数量减少 50%

### 辅助指标

| 指标 | 说明 | 目标 |
|------|------|------|
| 各平台平均引用率 | 各 AI 平台引用官方内容的问题比例 | 逐季提升 |
| P0 问题 Issue 认领率 | 已创建 Issue 中有 assignee 的比例 | ≥ 80% |
| 引用率改善周期 | 从 Issue 创建到该问题变为 satisfied 的平均天数 | < 60 天 |
| 评估流程耗时 | 全流程（sample → report）自动运行时间 | < 30 分钟 |
| 单次内容改进引用率提升 | 某 Issue 对应问题在 PR 合并后下次评估时 citation_rate 的绝对提升值 | > 0 |

## 六、范围

### MVP（v2.0）

- [x] 问题集生成（4 路径 + 手动输入 + doc_form 自动推断）
- [x] 官方 URL 预填充（三层审计：内容存在性 + doc_form 路径匹配 + HTTP 可达性）
- [x] AI 平台采样（ChatGPT、DeepSeek、豆包、Qwen、Gemini、Kimi）
- [x] 评分与诊断（URL 匹配 + doc_form 诊断路径 + GEO 建议目录）
- [x] Issue 创建与更新（per-question、GitHub + GitCode）
- [x] 评估报告生成（JSON + Markdown）
- [x] AGENT.md 全流程编排（6 步 + 参数化控制）
- [x] 支持多社区（通过 `.env` 配置切换）

### 后续版本

- [ ] 更多 AI 平台接入（Perplexity、通义灵码等）
- [ ] 定时自动化触发（OpenClaw 接入）
- [ ] 更细粒度的评分（引用位置权重、回答准确性评估）
- [ ] Web 可视化面板（引用率趋势图、Issue 状态看板）

### 明确排除

- **语义质量评估** — 不判断 AI 回答是否"讲对了"，只判断是否引用官方 URL
- **内容自动修改** — 系统只输出建议，执行靠内容团队人工操作
- **Web 管理界面** — Claude Code 对话 / CLI 驱动，无 UI

## 七、风险与缓解

| 风险 | 影响 | 概率 | 缓解策略 | 状态 |
|------|------|------|----------|------|
| AI 平台 API 不稳定或限流 | 高 | 中 | 单平台失败跳过；支持 append 模式补采样 | 已实现 |
