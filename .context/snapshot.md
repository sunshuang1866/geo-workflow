## 9. Product Background

### 项目背景

GEO (Generative Engine Optimization) Search Assessment System is an automated diagnostic platform that evaluates open-source communities' visibility and citation performance across major AI search platforms (ChatGPT, DeepSeek, Gemini, Qwen, etc.). The project addresses a fundamental shift in how developers discover information: instead of traditional search engines leading to official documentation, developers increasingly ask AI platforms directly and rely on the AI's synthesized answer as their first information touchpoint. This means communities must optimize for 'AI citation visibility' rather than traditional SEO rankings.

The system automatically samples AI platform responses to community-related questions, scores whether official content is cited, diagnoses gaps, and creates actionable GitHub/GitCode Issues to drive content improvements. It provides both real-time assessment and continuous monitoring (typically weekly) to track citation rate improvements over time.

### 用户画像

1. 社区运营负责人：评估官方内容在 AI 平台中的引用率表现，向管理层汇报 GEO 覆盖指标，优化内容策略
2. 技术文档团队：接收 GEO Issue 反馈，理解哪些内容官方 AI 未引用，执行针对性的文档改进和结构优化
3. DevOps/平台工程师：部署流水线，管理环境凭证，监控采样平台状态，维护 .env 配置和 Playwright 浏览器
4. Claude Code Agent（开发角色）：按照 SKILL 流水线执行评估步骤，处理数据转换，调用外部 API，管理文件状态，支持 dry-run 和幂等操作

### 使用场景

1. As a community operator, I want to establish a baseline GEO citation rate across multiple AI platforms, so that I can quantify how much the community's official content is visible in generative AI responses and identify which topics have the lowest citation coverage.
2. As a documentation team member, I want to receive structured Issues describing which content is not being cited by AI platforms and why, so that I can prioritize documentation improvements and measure their impact in the next assessment cycle.
3. As a platform engineer, I want to configure the system for a new open-source community by updating .env variables, so that the entire assessment pipeline runs automatically without code modifications.
4. As a DevOps team, I want to schedule weekly automated assessments via OpenClaw or Claude Code, so that I can continuously track citation rate improvements and detect regressions over time.
5. As a content team, I want to verify the impact of my documentation changes by re-running the assessment after submitting content PRs, so that I can confirm whether citation rate improved and close resolved Issues.
6. As a technical reviewer, I want to manually override or correct official_urls for specific questions before scoring, so that assessment results reflect accurate baseline expectations for what content should be cited.

### 关键设计决策（ADR）

1. ADR-001: Skill Chain Pipeline Architecture — Use 5 independent, loosely-coupled Skills chained via JSON files. Rationale: each step only reads upstream output and writes its own output; no bidirectional dependencies. Enables step-by-step recovery, human intervention points, and independent replayability. Impact: all state is persisted as JSON, queryable by humans, and no database is required.
2. ADR-002: File-Based State Management — All intermediate state (questions, responses, scores, issues) persists as JSON files in `output/{community_dir}/{date}/`. Rationale: enables human inspection, manual repair, and clear audit trails. Impact: requires explicit question-change detection in AGENT.md Step 0; `issue-map.json` uses append-or-update pattern for idempotence.
3. ADR-003: Minimal Human Intervention (Single Mandatory Touchpoint) — Only one required human action in the entire pipeline: filling `official_urls` in `questions.json`. All subsequent runs are fully automated. Impact: `prefill-urls` Skill provides LLM-assisted pre-fill, but humans must verify accuracy before scoring.
4. ADR-004: Configuration-Driven Multi-Community Support — Communities are switched by updating `.env` variables (GEO_COMMUNITY, GEO_COMMUNITY_DIR, etc.). No code changes needed. Impact: AGENT.md resolves all paths from .env; `output/` is isolated by community name.
5. ADR-005: Browser Automation Over API — `platform-chat` uses Playwright + Chromium for Web UI automation instead of platform APIs. Rationale: avoids dependency on unstable/restricted APIs, captures real user-facing experience. Impact: requires maintaining browser sessions and credentials; degrades gracefully when a single platform session expires.
6. ADR-006: Pure URL String Matching (No LLM-Based Citation Scoring) — `scoring-engine` uses exact + domain-level URL string matching, not LLM evaluation. Rationale: deterministic, auditable, no false positives. Impact: `official_urls` must be precise; citation judgments are binary (matched or not).
7. ADR-007: Issue Mapping via Suggestion Overlap — `issue-creator` uses `question_id` overlap (≥50%) to match suggestions to existing Issues for append-vs-create logic. Rationale: survives question rewording, handles multi-question Issues, and is human-verifiable via `issue-map.json`.
8. ADR-008: Step-by-Step Scorecard Reporting — `assessment-report` generates both `.json` (machine-readable) and `.md` (human-readable) outputs. Tracks iteration count per question for trend analysis. Impact: report generation is standalone (Step 4) and can be regenerated without resampling.
